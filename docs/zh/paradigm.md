# App 之后的设计软件

*作者：[西瓜飞船](https://xhslink.cn/o/42rk3ZEEuzY)*

*关于「软件即 skill」的笔记——以及当 agent 开始画图，设计工具会变成什么。*

英文原文：[docs/paradigm.md](../paradigm.md)

## 同一个循环，总是在同一个地方断掉

每次让 agent 设计一个产品页面，我都会撞上同一个失败。模型能写标记，工具却接不住。每一轮都要过一遍截图或导出，每一轮都丢掉一点东西：一个间距值、一个状态、一张卡片为什么在那里。agent 在写一种它没法检查的格式，而设计活在代码读不到的地方。

设计工具是为「坐在浏览器前的人」做的，它们非常擅长这件事。但当干活的人变成 agent，app 就成了障碍：设计在工具自己的文档里，agent 只能通过插件或截图够到它，交接给代码又是一次翻译。这条链上没有任何一环能被机器拒绝——你只能在浏览器里发现。

另一个方向错得不一样。给应用生成器一段提示词，你会得到一个能跑的应用——但设计是代码的副产品。代码出现之前没有东西可评审，代码变化时没有东西可 diff，下一次修改也没有一份能对照的持久规格。

两个循环都跳过了同一件东西：一份设计，简单到模型能写好、严格到工具能检查、又普通到能放进你的仓库。

这个产物就是本项目在讨论的东西。

## 两个赌注

**设计的产物应该是机器能检查的纯文本。** 不是带渲染器的私有格式——就是标记本身。一种能接受声明、能用理由拒绝、并且让同一个意图只有一种写法的格式，才是 agent 可以自己迭代、而不需要人在每一步盯着的格式。

**工具应该是 skill，不是 app。** app 意味着安装、账号、云端、更新通道、一个要保活的进程。skill 是 agent 需要时读取的一个目录：开工时打开工具，收工时放下。我把它叫做*随用随开*。

两个赌注是一体的。如果产物是一个文件，工具就不需要拥有它、托管它、让它一直热着。如果工具是 skill，第一次设计之前没有什么要安装，设计做完也没有什么要迁移。

## 产物是文件，不是文档

用浏览器打开设计，它就在那里。没有渲染器，没有 app，没有账号。它是一张合法的 HTML 文件：内联样式，一个元素一个节点，一页就是一个 `<section>`——所以 agent 拼出来的产物，和人双击打开的产物，是同一个东西。

由此有三件我在意的事：

- **它能 diff。** 改一个标题是 diff 里的一行，不是录屏里的一帧。设计可以在 pull request 里、挨着实现它的代码一起评审。
- **它能分发。** 把文件发出去，放进磁盘，附在工单上。收件人不需要这个工具，也不需要任何工具。
- **一个设计是一个文件，不是一屏一个文件。** 整个产品就是同一个文件里的多页——这才是 diff 和分发在规模上仍然成立的原因。

工具加上的不是一个容器，而是一组围绕文件的保证：每条声明要么被接受、要么被报告；文件保持规范形式；没人编辑过的文件会一个字节不变地回来；每个元素都有 `data-id`，所以一次编辑是一个字节区间，而不是重写。

## 工具是 skill，不是 app

| 没有 | 意味着什么 |
|---|---|
| 没有 MCP server | 没有要启动的进程，没有要改的客户端配置，模型和文件之间也没有协议。模型跑的是和你会敲的一样的命令。 |
| 没有要安装的 app | 没有要下载、更新或常驻的应用。skill 是一个目录；画布是 CLI 按需在本地起的页面，用完就关。 |
| 没有账号 | 不用登录、没有套餐、没有云端副本、没有使用量上报。设计文件就是唯一的状态，它就在你的 checkout 里。 |
| 没有构建步骤 | 源码就是运行物。改 checkout，装好的 skill 跟着变。 |
| 没有 `npm install` | 没有依赖，也没有 lockfile。没有东西要安装、审计或更新。 |

每少一样东西，就少一种「设计还没出现就先失败」的方式——进程没起来、会话过期、依赖解析成了别的东西、构建产物比源码旧。剩下的，就是一张能打开、能 diff、能提交的 HTML 文件，以及一套不会静默出错的命令。

## 工具是源码，不是二进制

app 交给你的是一组功能。skill 交给你的才是工具本身：CLI、格式、画布、校验器都是目录里的文件，而运行它们的 agent 也能读它们。这改变了「定制」的含义。在 app 里，厂商没预料到的需求会变成插件、需求单或者绕路；在这里，它会变成一次 diff：agent 读一下那条需要不同的命令，然后改掉它——为这个项目，今天就改。

这不是个小便利。这是「工具」和「材料」的区别。每个用这个 skill 的项目，最后都可能拥有一个略微不同的它——一条 token 命名规则、一个额外的校验器、一个只显示这个团队在意的东西的画布——而这些变体仍然共享同一个格式，所以文件在它们之间仍然可携带。一个基座，无穷变化。

这就是我说的 AI 原生，超出「模型来写标记」的那层意思：前沿不只在于 agent 能用软件，而在于软件能被使用它的 agent 读、fork、修改。二进制只能被使用；源码可以被生长。当工具是源码，工具就不再是「它能变成什么」的瓶颈。

## 哪些留给人类

一个完全由 agent 驱动的工具，也可以是一个反过来压过你的工具。我不想要那种东西。设计决策由 agent 做；真正重要的决定留给人：

- **审批。** agent 提出页面、问你，而不是静默发布。
- **指挥。** 在画布上指一个元素，复制指针，说要改什么。agent 从文件里读那个节点，一次只应用一个操作——每一个都有回执。
- **评审。** 设计是仓库里的一个文件。它能在 pull request 里评审、能回滚、能 diff、能和实现它的代码对照。

这就是我想要的新一代设计软件的形状：机器干活，人保留判断。不是一段产出像素的聊天，也不是一个把 agent 当成鼠标的 app。

## 实践：这个循环

九阶段展示的正是这种分工在真实会话里长什么样。Agent 负责 4 到 8——有格式、CLI 和画布的那一段。1–3 是产品对话；9 是写代码，代码由 agent 在你的仓库里完成，这个格式不覆盖它。

| # | 阶段 | Agent 做什么 | 你做什么 |
|---|---|---|---|
| 1 | 想法 | 用一句话复述产品，只问那些会改变页面的问题。 | 回答；如果复述得不对，就纠正它。 |
| 2 | 功能拆解 | 给出最小的第一版：核心循环、1–5 个各有职责的页面、空/加载/错误状态、数据，以及明确不做什么。 | 读一遍，指出缺的，或者该移出第一版的。 |
| 3 | 确认功能 | 只问一个明确的确认问题。你可以增删功能；问过之后它不再追问。 | 确认、增加、删除。 |
| 4 | 接管设计 | 说明它来设计页面，给出页面清单和一个视觉方向，然后创建（或打开已有的）设计文件并设置 token。 | 对页面清单或视觉方向提意见，或者让它继续。 |
| 5 | 先设计后写码 | 把顺序说一次：设计 → 确认 → 写码。 | — |
| 6 | 画布 | 打开本地画布，然后一页一页地搭，设计会逐步出现在已经打开的画布上。 | 让画布保持打开，跟着看。 |
| 7 | UI 调整 | 从文件里读取你指到的节点，一次只应用一个操作：`set`、`move`、`add`、`remove` 或 `tokens`。 | 在画布上选中一个元素，按 ⌘C（Windows/Linux 上是 Ctrl+C），把复制出来的指针粘贴回 agent 的对话框，说明要改什么。也可以直接在画布上拖动。 |
| 8 | 确认页面 | 跑一遍校验，过一遍清单——页面、状态、文案、图片、token——然后请你明确审批。 | 通过，或者退回去改。 |
| 9 | 实现代码 | 在你用的技术栈里逐屏实现这份已批准的设计；校验通过的设计文件就是规格。 | 审代码。 |

这条路是软引导，不是必须走完的关卡：agent 不问许可就开始，每个阶段都可以跳过，「直接做」优先，拆解按风险定轻重。两个入口会触发它——一个新的产品想法，以及新增或修改功能的请求，即使没说「设计」。如果只是在已有设计里改一处具体的东西，就不用走这条路。

## 代价

格式是故意收窄的：flexbox、绝对定位、固定的属性集合、内联 SVG、每个文本元素一段文字。没有 grid、没有 fixed、没有动画、没有响应式断点、没有富文本、没有多人协作、没有组件库。

这种收窄换来的是整个项目存在的理由：agent 会被按名字拒绝，而不是在浏览器里被发现；产物也小到能读懂。但代价是真实的，有些页面属于别的工具。如果设计需要一个活的组件系统、需要原型交互、或者需要一群人同时画，设计 app 仍然是正确答案。

这个赌注还可能以更深的方式赌错：如果界面变成 agent 拼装、没有人评审的东西，这个项目围绕的评审界面就不再重要。我不认为会走到那里——agent 建得越多，评审的重点越会从「画」转向「批」——但这是需要盯住的假设。

## 我认为它会走向哪里

如果工具可以是 skill，那么大多数「存在的意义是产出一个文件」的工具，都可以是 skill。app 从来不是价值所在；产物才是。当工具变成 agent 按需读取的一个目录，改变的不仅是分发方式——而是产物本身成了 agent、人、代码之间的接口。

这个仓库是这个想法的一个实例，选设计，是因为我能在这里把它从头到尾验证一遍：一种 agent 能检查的格式，一个人类能评审的画布，一张两边都留得住的 HTML 文件。同样的形状也适用于文档、图表，以及任何「真正的产出是某个必须被信任的文件」的东西。
